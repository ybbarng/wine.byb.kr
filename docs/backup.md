# 시음 기록 백업 — 설계

## 왜 필요한가

시음 기록은 **다시 만들 수 없는 유일한 데이터**다. 와인 이름·산지·품종·오크 같은 도감
정보는 전부 git 시드(`scripts/*.ts`)에 있어 서버가 비어도 배포 한 번이면 되살아난다.
하지만 직접 쓴 별점·감상·관측한 색·맡은 향·느낀 맛은 **앱으로만 들어가고 서버 DB에만
있다.** 잃으면 끝이다.

그런데 지금 그 데이터가 한 곳에만 있다.

- 원본 `data/wine.db`와 백업 `data/wine.db.bak.*`가 **같은 서버, 같은 폴더**에 있다.
  디스크가 죽거나 VPS가 사라지면 원본과 백업이 함께 사라진다.
- 서버 크론에 백업 작업이 없다(`heimdall` 한 줄뿐).
- **배포 횟수가 백업 이력을 잡아먹는다.** `./server`가 배포마다 백업을 남기고 14개만
  유지하는데, 하루에 배포를 여러 번 하면 14개가 그날치로 다 차서 그 이전이 날아간다.
  2026-09-06 유실 사고 때 실제로 8/31 이전 백업이 남아 있지 않아 복구가 불가능했다
  ([[wine-prod-deploy-data-safety]]).

## 용량은 문제가 아니다 (2026-09-07 실측)

| 항목 | 크기 |
|---|---|
| DB 전체 `wine.db` | 280 KB |
| 시음 기록 60건 JSON 덤프 | 34 KB (gzip 5 KB) |
| 시음 기록 순수 텍스트 | 5 KB |

사진 한 장보다 작다. 서버 백업 14개를 다 합쳐도 4 MB다. **그러니 "얼마나 자주, 어디에"
를 아낄 이유가 없다.** 지금 구조의 문제는 용량이 아니라 **위치**(한 곳에만 있음)와
**이력 깊이**(배포가 덮어씀)다.

## 쓸 수 있는 자산 — 홈 서버에 이미 있다

`health.byb.kr`(홈 서버 `home.byb.kr`에서 운영)이 같은 문제를 이미 잘 풀어 뒀다.
`health.byb.kr/ops/health-backup.sh` 참고.

- `~/bin/rclone` + 인증이 끝난 `gdrive:` 리모트 → 구글 드라이브 업로드
- GPG 대칭 암호 파일 `~/.config/ha-backup/passphrase` (HA 백업과 공유)
- 실패 시 폰 알림(Home Assistant 웹훅), 구글 토큰 만료를 따로 구분해 안내
- 순환 정책: 로컬 5개 / 드라이브 30개
- 업로드가 실패해도 로컬 사본은 남기는 구조
- **암호는 백업 안에 넣지 않는다**(암호화된 파일에 열쇠를 같이 넣으면 무의미) —
  비밀번호 관리자에 따로 보관

## 그런데 wine 서버는 인프라가 다르다 (2026-09-07 확인)

wine.byb.kr은 홈 서버가 아니라 **byb.kr VPS**에서 돈다. 위 자산이 거의 없다.

| 항목 | byb.kr 상태 |
|---|---|
| rclone | 없음 (바이너리도, 구글 토큰도) |
| GPG 암호 파일 | 없음 (단 `gpg` 바이너리는 있음) |
| sqlite3 | **없음** → `.backup`으로 일관 스냅샷을 뜰 수 없다 |
| sudo | 비밀번호 필요 → `apt install` 불가 |
| HA 웹훅 | 없음 (다른 호스트라 해당 없음) |

## 방향 세 가지

### A. 홈 서버가 당겨온다 (pull) — 본격 백업으로 이걸 택한다

홈 서버 크론이 byb.kr에 SSH로 붙어 DB 스냅샷을 받아온 뒤, **health와 똑같은
gpg + rclone 파이프라인**에 태운다.

- rclone 토큰·GPG 암호·폰 알림·순환 정책을 **그대로 재사용**한다. 새로 만들 건
  `wine-backup.sh` 하나와 크론 한 줄(예: 04:40 — HA 04:00, health 04:20 다음).
- **byb.kr에 새 비밀을 하나도 두지 않는다.** 이게 핵심이다. byb.kr은 인터넷에 열린
  VPS라, 거기에 구글 드라이브 토큰과 복호화 암호를 두면 그 서버가 뚫렸을 때 백업까지
  함께 털린다. 당겨오는 방식은 그 위험이 없다.
- sudo 불가·sqlite3 없음 문제도 우회된다(홈 서버엔 둘 다 있다).
- 스냅샷 뜨는 법: byb.kr에 sqlite3가 없으므로 앱이 이미 쓰는 `pnpm exec tsx`로
  덤프하거나(아래 C의 덤프 스크립트를 재사용), 서비스를 멈추지 않고 파일을 그대로
  받아오되 무결성을 검증한다. **일관성이 보장되는 방법을 쓸 것** — 쓰기 도중 파일을
  그냥 복사하면 깨진 스냅샷이 될 수 있다.
- 단점: 홈 서버가 꺼져 있으면 그날은 거른다. 그리고 이건 wine 저장소가 아니라 **홈 서버
  운영 영역** 작업이라, SSH 키 배치는 사람이 해야 한다.

### B. wine 서버에 push 파이프라인 심기 — 택하지 않는다

health와 똑같이 byb.kr에 rclone·GPG 암호·크론을 두는 방식. rclone은 `~/bin`에 sudo
없이 깔 수 있지만,

- 구글 OAuth를 byb.kr에서 **대화형으로** 해야 한다(자동화 불가, 사람이 개입).
- 구글 토큰과 복호화 암호를 인터넷 노출 VPS에 두게 된다 → A보다 위험하다.
- 알림 채널을 새로 만들어야 한다(HA 웹훅이 없다).

### C. 시음 기록을 JSON으로 git 커밋 — A와 함께 간다

배포 때마다 시음 기록을 JSON으로 덤프해 저장소에 커밋한다.

- **저장소가 PRIVATE인 것을 확인했다.** 개인 기록을 담아도 공개되지 않는다.
- 34 KB짜리 파일이라 바뀐 줄만 diff로 쌓인다. 10년을 매일 커밋해도 몇 MB다.
- **변경 이력이 남는 게 진짜 이득이다.** 지난 사고 때 백업 파일 14개를 하나씩 받아
  대조하며 유실 시점을 특정했는데, JSON이 git에 있으면 `git log -p`로 즉시 끝난다.
- 서버 설정이 필요 없어 저장소 안에서 완결된다.
- 한계: 암호화가 없고(비공개 저장소에 의존), GitHub에 의존한다. 그래서 A를 대체하지
  않고 **함께** 간다.

## 결정

- **C를 먼저 한다** → **완료(2026-09-08)**. 매일 04:00 KST 자동 백업이 돈다.
- **A는 보류한다.** 처음엔 "이어서 한다"였는데, C가 돌기 시작하니 급하지 않다고 판단을
  바꿨다. 아래 '지금 남은 위험' 참고.
- **B는 하지 않는다.** 인터넷 노출 서버에 백업 열쇠를 두는 건 백업을 같이 잃는 길이다.

### 지금 남은 위험 (C가 돌기 시작한 뒤 다시 따져봄, 2026-09-08)

| 위험 | 상태 |
|---|---|
| 서버 소멸·삭제·시드 버그 | C가 덮는다 |
| 하루치(최대 24시간) 구멍 | 해당 없음 — 주 1~2회 마시는 페이스라 충분하다 |
| 예약 워크플로 60일 자동 비활성화 | **해당 없음 — 공개 저장소만 적용**되고 이 저장소는 비공개다 |
| GitHub 한 곳 의존 | 남음 → A가 푸는 문제. 다만 확률이 낮고 로컬 클론도 있다 |
| 백업 실패를 모르고 지나감 | 남음 → A 없이도 알림 한 줄로 값싸게 막을 수 있다 |

> 60일 규칙은 한때 "비공개도 해당된다"고 잘못 알고 A를 서둘러야 한다고 봤다. GitHub 공식
> 문서가 *"In a **public repository**, scheduled workflows are automatically disabled when no
> repository activity has occurred in 60 days"* 라고 못박고 있어 이 저장소엔 해당되지 않는다.

## 구현 스케치

### C — git JSON 백업

**1단계(완료)** — 덤프·복구 스크립트와 기준 스냅샷:

- `scripts/dump-tastings.ts` → `backup/tasting-notes.json` (37 KB, 60건).
  형식·정렬 규칙은 `src/features/journal/tasting-backup.ts`에 두고 테스트로 고정했다.
  - **와인은 `id`가 아니라 `slug`로 참조한다.** id(cuid)는 DB를 다시 만들면 바뀐다.
  - **"내보낸 시각" 같은 필드를 넣지 않고 정렬을 고정한다.** 안 그러면 내용이 그대로여도
    매번 diff가 생겨 헛커밋이 쌓인다.
  - `--stdout`으로 파일 대신 표준출력에 쓸 수 있다(원격에서 긁어올 때).
  - `isPublic` 여부와 무관하게 전부 담는다 — 백업 기준은 "화면에 보이는 것"이 아니라
    "잃으면 안 되는 것"이다.
- `scripts/restore-tastings.ts` — **없는 기록만 넣고 있는 기록은 건드리지 않는다.**
  기본은 미리보기고 `--write`를 붙여야 실제로 넣는다. 원래 id를 그대로 살려 두 번 돌려도
  중복이 생기지 않는다.
- 백업 파일은 `/data/`가 아니라 **저장소 루트 `backup/`**에 둔다. `/data/`는 DB를 지키려고
  통째로 gitignore돼 있고, 거기에 예외를 뚫으면 실수로 DB를 커밋할 위험이 생긴다.
- 실제 프로덕션 데이터로 검증한 것: ① 두 번 돌려도 같은 파일 ② 지운 기록 1건이 전 필드
  그대로 복구됨(나머지 59건 무변화) ③ 두 번 복구해도 중복 없음 ④ **복구가 수정된 기록을
  덮어쓰지 않음**.

**2단계(완료)** — 자동 실행. 매일 04:00 KST + 수동 실행.

`SERVER_SSH_KEY`는 **forced-command 키**(지금은 `command="./servers/byb.kr/apps/wine/deploy.sh"`, 처음엔 `./server`)라
Actions에서 임의 명령을 돌릴 수 없다. 그래서 **백업 전용 키를 따로** 뒀다 — 권한을 가르는
게 핵심이다. 이 키는 덤프 하나만 실행할 수 있어, 새어도 기록을 읽는 것 외엔 못 한다.

- 덤프 래퍼 — forced-command로 실행된다. 2026-10-20 컨테이너로 옮기면서 `ops/dump-tastings-remote.sh`(nvm·`.env` 를
  불러 pnpm 으로 실행)를 지우고 `servers` 저장소의 `byb.kr/apps/wine/dump-tastings.sh` 로 바꿨다. `tools` 이미지로
  `scripts/dump-tastings.ts --stdout` 을 돌린다. 받는 쪽이 stdout을 그대로 파일로 쓰므로 **JSON만 내보내고** 잡음은 버린다.
- `.github/workflows/backup.yml` — 커밋 전에 검사한다: 비었는지 · 유효한 JSON 배열인지 ·
  **기록 수가 줄지 않았는지**. 줄었으면 커밋하지 않고 실패시켜 사람이 보게 한다. 깨진
  파일로 백업을 덮으면 백업이 아니라 손실이기 때문이다. 바뀐 게 없으면 커밋하지 않는다.
- 서버 `authorized_keys`에 백업 전용 공개키 한 줄, GitHub 시크릿 `BACKUP_SSH_KEY`.
- ⚠️ **로컬에서 이 키를 시험할 땐 `-o IdentitiesOnly=yes`가 필요하다.** 없으면 ssh가
  에이전트 키·기본 `id_ed25519`도 함께 제시해 제약 없는 키로 붙고, forced-command가 안
  걸려 평범한 셸이 열린다(`whoami`가 그대로 실행돼 설정이 틀린 줄 오해하기 쉽다).
- ⚠️ 서버에서 직접 커밋·푸시하는 방식은 피했다. `./server`가 안에서 `git pull`을 해
  충돌할 수 있다.
- ⚠️ `server` 스크립트 자체를 고치면 **그 변경은 다음 배포부터** 적용된다
  ([[wine-prod-deploy-data-safety]]).

### A — 홈 서버 pull 백업 (보류, 나중에 할 때 이 스케치대로)

- `ops/wine-backup.sh` (이 저장소에 두고 홈 서버 `~/bin/`에 배치) —
  `health-backup.sh`를 본떠 만들되 대상만 wine으로 바꾼다.
- 홈 서버 → byb.kr SSH 키를 만든다. **`~/.ssh/wine_deploy`는 절대 쓰지 않는다**
  (forced-command라 접속하면 배포가 실행된다). 읽기 전용 목적의 별도 키를 쓴다.
- 홈 서버 크론에 한 줄 추가(예: `40 4 * * *`).
- 담을 것: `data/wine.db` 스냅샷. 서버 `.env`(ADMIN_PASSWORD 등 저장소에 없는 값)도
  함께 담을지는 결정 필요.

## 열린 질문

- ~~C의 덤프·커밋을 어디서 돌릴까~~ → **결정: 서버에서 push하지 않는다**(`./server`의
  `git pull`과 충돌). Actions가 당겨와 커밋한다. 다만 **당겨오는 방법**은 아직 안 정했다
  (백업 전용 SSH 키 vs 관리자 인증 내보내기 엔드포인트 — 위 2단계 참고).

  사용자 입력이라 유실 대상이다. 시음 기록만으로 시작하고 넓히는 게 안전하다.
- `data/seed/`(초기 CSV·시음 노트 원문)도 gitignore돼 저장소에 없다. 시드의 출발점인데
  서버·로컬에만 있는 셈이라, 이것도 백업 대상인지 따로 판단이 필요하다.
- A에서 서버 `.env`(비밀)를 백업에 포함할지. health는 포함하되 **GPG 암호는 제외**한다.
