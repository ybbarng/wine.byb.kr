# 가이드 시음 (Guided Tasting) — 설계

## 목표

지금의 시음 기록은 "다 마신 뒤 결과를 적는" 폼이다. 가이드 시음은 한 걸음 더 나아가,
**와인을 따는 순간부터 곁에서 안내하며 함께 시음**하게 한다. 각 단계에서 단순히
"보고 평가하세요"가 아니라, **이 와인은 이런 상태일 것이다(예상)** 와 **왜 그런가(근거)**
를 먼저 알려주고, 사용자가 그걸 실제로 확인·평가하게 한다.

예: "이 와인은 잔 벽을 타고 흐르는 눈물자국(legs)이 굵을 거예요 — 알코올·당분이 높은
편이라서요. 스월해보고 확인해보세요." → 사용자가 확인/체크.

관련: [[wine-experience-goals]] 의 '신기하다' 목표와 맞물린다. 기록이 곧 학습이 되게.

## 원칙 (결정됨)

- **단일 흐름**: "빠른 기록 모드"를 따로 두지 않는다. 지금의 기록 마법사 한 흐름에 각 단계의
  "예상 + 근거" 안내를 얹는다. 빠른 기록은 "그 흐름을 빠르게 지나가는 것"으로 자연히 해결.
- **가이드는 강제가 아니라 곁들임**: 모든 단계는 건너뛸 수 있고, **와인만 고르면 언제든 저장**
  가능해야 한다(지금 마법사의 "언제든 저장" 구조 유지). 향 확인·맛 평가를 진행 조건으로 걸지
  않는다 — 걸면 빠른 기록이 죽는다.
- **기존 입력은 절대 유실되지 않는다**: 가이드용 새 필드·단계를 추가해도, 이미 입력된 값은
  어떤 편집·배포에도 지워지지 않아야 한다. 편집 저장은 **PATCH 부분 갱신**(온 칸만), 시드는
  **빈 칸만 채움** 규칙을 반드시 지킨다. ([[wine-prod-deploy-data-safety]] — 이 규칙을 어겨
  실제 리뷰가 유실된 사고가 있었다.)

## 흐름 (실제 시음 순서)

마신 기록 마법사(`tasting-note-wizard.tsx`)의 단계 순서를 그대로 잇되, 각 단계에 "예상 +
근거 + 확인" 레이어를 얹는다.

1. **고르기** — 어떤 와인인지 선택(기존).
2. **붓기·색** — "따라서 잔을 기울여 색을 보세요."
   - 예상: 이 와인은 `이런 색`일 거예요. (근거: 종류·품종·빈티지)
   - 확인: 실제 색을 컬러피커로 맞춰 기록(기존 색 단계).
3. **스월·외관** — "잔을 돌려 점도와 눈물자국을 보세요."
   - 예상: 바디가 `가벼움/중간/무거움`이라 눈물자국이 `이럴` 거예요. (근거: 품종 body)
   - 확인: 스월 잔 프리뷰와 비교, 느낌 체크.
4. **향** — "코를 대고 향을 맡아보세요."
   - 예상: `자두·바닐라·후추…` 같은 향이 예상돼요. (근거: 품종 aromaProfile, notesKo)
   - 확인: 예상 향 목록에서 **실제로 난 향을 고른다**(다중 선택) + 자유 메모.
5. **맛** — "한 모금 머금어보세요."
   - 예상: 산도 `높음`, 타닌 `중간`, 단맛 `없음`, 바디 `무거움`. (근거: 품종 acidity/tannin/sweetness/body)
   - 확인: 각 축을 실제로 느낀 정도로 평가(예상과의 일치도) + 예상 맛 체크.
6. **종합** — 별점·가격 대비·재구매(기존 verdict).

## 각 단계의 "예상 + 근거" — 데이터 매핑

근거 데이터는 대부분 이미 있다.

| 단계 | 예상 표시 | 근거(출처) |
|---|---|---|
| 색 | 예상 색 스와치 | `Wine.colorHex` → 없으면 `type`·품종 추정(`wineGlassFor`) |
| 스월·외관 | 바디→점도/legs 문구 | `Grape.body` |
| 향 | 예상 향 태그들 | `Grape.aromaProfile`(JSON 배열), `Wine.notesKo` |
| 맛 | 산도·타닌·단맛·바디 게이지 | `Grape.acidity`·`tannin`·`sweetness`·`body` |
| 음식 | 어울리는 음식 | `Wine.foodPairing`(JSON 배열) |
| 한마디 | "마시는 순간 뭘 느껴볼지" | `Wine.notesKo`(이미 이 용도로 큐레이션됨, [[wine-notes-content-direction]]) |

블렌드는 `WineGrape`(품종+비율)로 여러 품종의 향·특성을 비율 가중해 합친다.

**콘텐츠 공백**: `Grape.aromaProfile`·`body`·`acidity`·`tannin`·`sweetness`가 비어 있는
품종이 있다. 가이드 품질은 이 데이터 채움에 비례한다 → 품종 데이터 보강이 실제 작업의
큰 몫(코드보다 콘텐츠). `/add-wine` 큐레이션 흐름([[wine-add-new-gap]])에 품종 특성·향
채우기를 포함시키면 자연히 축적된다.

## 저장 (가이드 결과)

가이드에서 사용자가 "확인/평가"한 것을 남기려면 `TastingNote`에 필드가 필요하다.
SQLite라 JSON 문자열로 둔다(기존 `foodPairing`·`aromaProfile`과 동일 방식).

- `aromasConfirmed String?` — 예상 향 중 실제로 맡은 것들(JSON 배열).
- `flavorFelt String?` — 산도/타닌/단맛/바디를 실제로 느낀 정도(JSON: `{acidity:1..5, ...}`).
- (선택) `guidedAt DateTime?` — 가이드로 기록했는지 표시.

기존 필드(`rating`·`colorHex`·`bodyText`·`value`·`repurchase`)는 그대로 재사용.
**주의**: 새 필드는 편집 저장(PATCH 부분 갱신)·시드(빈 칸만 채움) 규칙을 반드시 따른다
— 데이터 유실 사고의 교훈([[wine-prod-deploy-data-safety]]).

## 구현 페이즈

작게 시작해 단계별로 넓힌다(각 페이즈 = 별도 PR).

- **P1 — 색 단계에 "예상 + 근거" 문구**: 기존 색 단계에 "이 와인은 이런 색일 거예요(종류·품종
  때문)" 한 줄과 예상 색 스와치를 붙인다. 저장 변화 없음. 가장 작은 검증.
- **P2 — 향 단계**: 예상 향 태그(`aromaProfile`) 표시 + 실제 맡은 향 다중 선택. `aromasConfirmed`
  필드 추가.
- **P3 — 맛 단계**: 산도/타닌/단맛/바디 예상 게이지 + 실제 느낌 평가. `flavorFelt` 필드 추가.
- **P4 — 스월·외관 단계**: 바디→legs 안내 + 스월 프리뷰 강조.
- **P5 — 다듬기**: 근거 문구 카피 정리, 블렌드 가중 합성, 품종 콘텐츠 보강 캠페인.

## 열린 질문 (P2·P3에서 결정)

- ~~가이드/빠른 기록 모드 분리 여부~~ → **결정: 단일 흐름 + 곁들이는 안내**(위 '원칙' 참고).
- 예상과 실제의 "일치도"를 점수화해 보여줄지(재미 요소) vs 부담이 될지. (향·맛 단계 P2·P3 때)
- 품종 향·특성 데이터 소스를 어디까지 자동 큐레이션(웹 검증)할지. (P2·P3 때)
